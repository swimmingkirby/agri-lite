# Agri-Lite

A web application that simulates and visualises soil moisture, air
temperature and light readings for small-scale and DIY growers. It
generates plausible environmental data on a recurring schedule, stores
it in a hosted Postgres database, and surfaces it through a real-time
dashboard with configurable per-plot threshold warnings, historical
time-series charts, and a grower-notes log.

The project was undertaken as a final-year BSc dissertation submission
at the University of Portsmouth and is intended both as a working
artefact and as the implementation evidence for the accompanying
written report.

## 1. Project context

Existing precision-agriculture tooling assumes a level of sensor
investment and configuration overhead that excludes hobbyist growers.
Agri-Lite is a software-only response to that gap: by simulating the
environmental signals a hobbyist might gather, it lets a user explore
what a precision-monitoring dashboard *could* offer them before they
commit to any hardware purchase. The application is therefore framed
explicitly as an exploration tool, not as a sensor-reading product.

All readings are generated by a deterministic random-walk simulator
(documented in [`lib/simulator.ts`](lib/simulator.ts)) rather than
collected from physical sensors. This is a deliberate scope decision
documented at the start of development; nothing in the application
purports to be live agronomic data.

## 2. System architecture

The application is a single Next.js project deployed to Vercel as
serverless functions, with a managed Supabase Postgres instance
providing persistence and a real-time event channel. There is no
authentication layer — the application is a single-user demonstrator
by deliberate scope decision.

```
                  ┌────────────────────────────────────┐
                  │  Browser (Next.js client)          │
                  │  · React Server / Client split     │
                  │  · Recharts time-series + spark    │
                  │  · Supabase realtime subscription  │
                  └─────────────┬──────────────────────┘
                                │  fetch (anon key, RLS-restricted)
                                ▼
                  ┌────────────────────────────────────┐
                  │  Next.js API routes (Vercel)       │
                  │  · /api/plots                      │
                  │  · /api/readings                   │
                  │  · /api/thresholds                 │
                  │  · /api/notes                      │
                  │  · /api/cron/simulate (auth-gated) │
                  │  · /api/seed (auth-gated)          │
                  └─────────────┬──────────────────────┘
                                │  service-role key (bypasses RLS)
                                ▼
                  ┌────────────────────────────────────┐
                  │  Supabase (Postgres + Realtime)    │
                  │  · plots, readings, thresholds,    │
                  │    notes (RLS: anon read-only)     │
                  │  · pg_cron + pg_net + Vault        │
                  │    drive the simulator every 60s   │
                  └────────────────────────────────────┘
```

## 4. Running locally

The application can be reproduced locally against a fresh Supabase
project in approximately five minutes.

### 4.1 Provision Supabase

1. Create a new free-tier project at <https://supabase.com>.
2. From the project dashboard, copy the project URL, the anonymous
   public key and the service-role key. The service-role key must
   never reach the browser.
3. In the SQL Editor, apply
   [`supabase/migrations/0001_initial.sql`](supabase/migrations/0001_initial.sql)
   to create the four tables and Row Level Security policies.
4. Under **Database → Replication**, add the `readings` table to the
   `supabase_realtime` publication so the dashboard's real-time
   subscription receives `INSERT` events.

### 4.2 Configure environment variables

```bash
cp .env.local.example .env.local
# Then populate .env.local with the values from step 4.1 plus a long
# random hexadecimal CRON_SECRET.
```

The four required variables are:

| Variable                         | Used by              | Purpose                                  |
| -------------------------------- | -------------------- | ---------------------------------------- |
| `NEXT_PUBLIC_SUPABASE_URL`       | server + browser     | Supabase project URL                     |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY`  | browser only         | Anonymous JWT, RLS-restricted to SELECT  |
| `SUPABASE_SERVICE_ROLE_KEY`      | server only (secret) | Bypasses RLS for API-route writes        |
| `CRON_SECRET`                    | server only (secret) | Bearer token guarding the cron endpoint  |

### 4.3 Run

```bash
npm install
npm run dev
```

Visit <http://localhost:3000>, create a plot from the sidebar, then
manually trigger the simulator to insert the first reading:

```bash
curl -X POST http://localhost:3000/api/cron/simulate \
  -H "Authorization: Bearer ${CRON_SECRET}"
```

The dashboard updates without a page reload via the Supabase real-time
subscription.

## 5. Deployment

The repository is wired to deploy automatically when commits land on
`main`. To reproduce the deployment from scratch:

1. Push the repository to GitHub.
2. Import the repository in Vercel as a new project (the framework
   preset auto-detects as Next.js).
3. Set the four environment variables under **Project Settings →
   Environment Variables**, marking `SUPABASE_SERVICE_ROLE_KEY` and
   `CRON_SECRET` as *Secret*.
4. Deploy. Vercel reads [`vercel.json`](vercel.json) and registers the
   daily cron job at `/api/cron/simulate`, automatically attaching an
   `Authorization: Bearer ${CRON_SECRET}` header to its requests.

### 5.1 Free-tier scheduling

Vercel's Hobby plan caps cron jobs at one execution per day, but the
intended simulator cadence is once per minute. The deployed
`vercel.json` therefore registers the route at `0 6 * * *` (06:00 UTC
daily) as an architectural marker that the API works under Vercel
Cron, while the actual one-minute cadence is provided by a
Supabase-side `pg_cron` job that posts to the same endpoint. The
bearer token is held in Supabase Vault rather than inlined in the
cron job body. The complete configuration is in
[`supabase/migrations/0002_pg_cron_simulator.sql`](supabase/migrations/0002_pg_cron_simulator.sql).

## 7. Demonstration scenarios

To exercise the dashboard against environmental conditions that would
take days to occur naturally under the live simulator's drift, the
application includes a scenario seeder reachable at
`POST /api/seed`. Each scenario biases the same random walk used by
the live simulator toward a predetermined target curve over a 30-day
window, then upserts the corresponding notes and threshold settings.
The endpoint is auth-gated by the same `CRON_SECRET` as the cron
route.

| Scenario             | Window  | Demonstrates                                                        |
| -------------------- | ------- | ------------------------------------------------------------------- |
| `healthy`            | 30 days | Baseline operation with four weekly watering events                 |
| `drought`            | 30 days | Three drought-and-recovery cycles of varying severity               |
| `heatwave`           | 30 days | Three heatwaves of varying intensity (moderate / severe / brief)    |
| `light_deprivation`  | 30 days | Predominantly cloudy month with two short sunny breaks              |
| `mixed`              | 30 days | Composite month combining drought, heatwave and cloudy stretches    |

Example invocation:

```bash
curl -X POST https://agri-lite-woad.vercel.app/api/seed \
  -H "Authorization: Bearer ${CRON_SECRET}" \
  -H "Content-Type: application/json" \
  -d '{"plot_id":"<uuid>","scenario":"drought"}'
```

The seeder wipes the target plot's existing readings, notes and
thresholds before inserting so each scenario remains self-contained.
The live simulator continues adding new readings every minute on top
of the seeded history.
